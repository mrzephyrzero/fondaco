| 2026-11-15 | Schema names are matched exactly against the dialect-normalized tree | Catalog names are exact; the database itself resolves unquoted identifiers by the dialect's case rule. A mismatch is an unknown relation (deny), never a fuzzy match |

| 2026-11-15 | Plan DSL v2: templates may begin with `WITH` (non-recursive, read-only CTEs); `WITH RECURSIVE` refused by the parser | Approved by the maintainer. | 2026-11-15 | Prompt v4 becomes the default | Teaches column-level labeling and enum-value filtering; v3 kept for reproducibility |
| 2026-11-15 | MCP server is a separate process proxying a JSON API v1 of the running boundary, not a second boundary | One place holds plan state, the audit chain and DB credentials. Human approvals in the UI and agent calls see the same records. The MCP process can be compromised without exposing data access |
| 2026-11-15 | No approve/reject tool or endpoint for agents; agent-written steps cross `assemble_plan` + the validator, and the boundary assigns `plan_id` | Approval stays a human act (V1's core promise). A client-chosen id could overwrite a record a human is reviewing |
| 2026-11-15 | Under the JSON API an auto-approved plan waits in `approved` until `execute` is called; the UI still runs it on submission | Matches the MCP propose/execute split without changing the V1 UI flow |
| 2026-11-15 | Optional bearer token (`FONDACO_API_TOKEN`) on `/api/v1` only | Smallest step toward agent authentication without touching V1's unauthenticated UI (documented residual, threat 23) |
| 2026-11-15 | `FONDACO_SQL_DIALECT` must match the selected adapter or the app refuses to start | The boundary must parse plans in the grammar the database executes; a silent mismatch could make the analyser and the database disagree on what a template reads |
| 2026-11-15 | SQL Server: `ApplicationIntent=ReadOnly` forced, `readonly=True`, query timeout, `LOCK_TIMEOUT`, default-schema check; labels from `MS_Description` | Read-only at every layer the driver controls. Bare names must resolve to the exposed schema. Extended properties are SQL Server's native counterpart to Postgres comments |
| 2026-11-15 | BigQuery: dry-run gate on `statement_type == SELECT`, `maximum_bytes_billed`, `job_timeout_ms`, one `default_dataset`, base tables only | BigQuery's own parser confirms read-only before any byte is read. Cost and time are capped by the service, not only by the client |
| 2026-11-15 | SQL Server: refuse any login whose effective permissions (database, schemas, tables and views) include anything outside an allow-list of reads | Live testing showed `ApplicationIntent=ReadOnly` and `readonly=True` are hints a standalone server ignores: a db_owner login committed `INSERT …; COMMIT; SELECT 1`. An allow-list fails closed on permissions added in later releases |
| 2026-11-15 | BigQuery: the adapter re-parses the template with `boundary.sql_ast.parse_template` before the dry run; every API call gets the statement timeout as its timeout and retry deadline, and a timed-out job is cancelled | The dry run trusts one field from the service (the emulator reports every statement as SELECT, and a write ran). The SDK's default retry deadline is 600 s, so a 1 s budget did not hold |
| 2026-11-15 | Live adapter tests are a separate workflow (`live-adapters.yml`): on demand, weekly, and when the adapters change | Two extra images and an ODBC driver install do not belong in every CI run; drift in drivers and engines still gets caught |
| 2026-11-15 | Risk-proportional auto-approval (`boundary/approval_policy.py`), off by default; cap `internal`, `restricted` never configurable; every query step must be fully resolved by the analyser; results under `auto_approve_min_rows` (after the k-threshold) are held for a human | Removes the human from routine low-risk reads without moving the boundary: the policy engine still decides allow/deny, auto-approval only decides who clicks. Small results are where inference risk concentrates, so release (not execution) is what they wait for. Actor `auto-approval-policy` in the same audit chain |
| 2026-11-15 | Auto-discovery lives in `executor/discovery/` (CLI `fondaco discover`), not a new top-level package | The repository layout is fixed (CLAUDE.md); discovery reads sources the way adapters do, so it sits beside them and is never imported by `boundary/` |
| 2026-11-15 | Discovery is deterministic and local: check-digit detectors (codice fiscale, partita IVA, IBAN mod-97) plus email/phone/IP and whole-token name hints; at most 500 rows per table in memory; it never proposes `public` | No LLM and no network beyond the scanned database, so onboarding a source sends nothing anywhere. Check digits keep random codes from passing as PII; erring upward is the only allowed mistake, and publishing is a human decision |
| 2026-11-15 | Discovery output is a proposal (`review_required: true`); the reviewed JSON feeds only `enum_values`/`business_description` through `FONDACO_SCHEMA_ANNOTATIONS`, never labels | Labels stay where they were (source comments), so a wrong or stale proposal cannot lower a label; metadata is applied only where the source's effective label is public/internal |
| 2026-11-15 | `sqlite` joins the supported dialects; a relation name containing `/ \ : .` is refused as a path in every dialect | Embedded engines (DuckDB, SQLite) read files by name (`FROM 'x.csv'`); refusing path-shaped names at parse time keeps that out before any schema lookup. A real table with such a quoted name is refused too — fail closed |
| 2026-11-15 | DuckDB adapter (`FONDACO_ADAPTER=duckdb`) reads labels from a reviewed `schema.yaml`/`.json` in the `fondaco-annotations` format; unlisted tables/columns are `restricted` | An embedded file or a folder of CSVs has no catalog comments to carry labels. Reusing the discovery output format means `fondaco discover --duckdb` → review → run, with no second format to learn |
| 2026-11-15 | The DuckDB engine is locked at open: `read_only=True`, `enable_external_access=false`, no extension autoinstall/autoload, `lock_configuration=true`, timer-based interrupt, memory/thread caps. CSV/Parquet/SQLite sources are loaded first into a new file by a separate, closed connection; SQLite goes through stdlib `sqlite3`, not a DuckDB extension | An in-process engine can read the host filesystem; the boundary already refuses such templates, and the engine must refuse them again on its own (defense in depth). Building before opening keeps the serving connection free of any external access |
| 2026-11-15 | One `fondaco` command dispatching to `discover`, `mcp`, `serve` (and `demo`) in `api/cli.py`; `fondaco-mcp` kept as an alias | One entry point to document; each subcommand imports only what it drives, so `discover` never loads the web app |
